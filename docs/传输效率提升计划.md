# 传输效率提升计划

针对「网关与客户端在 HTTP 压缩、SSE/WS 流式支持上普遍缺失」这一痛点，本文件记录对两个参照实现的实测调研结果，以及 lite-cpa 的分阶段提升计划。

- 参照实现 A：[router-for-me/CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI)（下称 **CPA**）
- 参照实现 B：[xz-dev/AI-gateway](https://github.com/xz-dev/AI-gateway)（下称 **AI-gateway**）及其关键中间件 [xz-dev/ai-sse-keepalive-proxy](https://github.com/xz-dev/ai-sse-keepalive-proxy)（下称 **keepalive-proxy**）
- 对象：lite-cpa（本仓库）

所有结论均来自实际 clone 后的代码检索与本地运行数据，证据出处标在每一条后面。**未经验证的部分单独标注为假设**。

---

## 1. 结论摘要

1. **lite-cpa 在下游零压缩**：没有任何响应压缩代码，也没有 gzip/zstd/brotli 依赖。这是最大的、最便宜的浪费点，且 lite-cpa 自己持有 downstream writer，改造只在一处。
2. **上游压缩是「Go 标准库的意外福利」**：非流式路径由 `net/http` 自动注入 `Accept-Encoding: gzip` 并透明解压，所以上游出口其实已经在压缩；但 Claude 流式路径被硬编码成 `identity`，主动放弃了这份收益。（`internal/executor/executor.go:455`）
3. **客户端压缩请求体完全不被接受**：`limitBody` 只做 `http.MaxBytesReader`，不识别 `Content-Encoding`，客户端发 gzip/zstd 请求体会直接解析失败。（`internal/server/server.go:472`）而 Codex CLI / Kimi / opencode 的二进制里都带 zstd 与 `Content-Encoding` 处理能力。
4. **两条流式健壮性缺失**：无 WS 支持（全仓库 0 处 Upgrade/websocket）；无 SSE 保活（上游静默期不写任何字节）。
5. **CPA 的强项是 WS（增量 WS 有完整实现），弱项同样是下游压缩**——它也没有下游响应压缩。keepalive-proxy 的强项是「静默期保活帧」，并且它的 README 明确论证了：普通 APISIX/Nginx body filter 无法在静默期产出字节，必须由流式反代持有 downstream writer。**这正是 lite-cpa 的架构位置**，所以保活应当内建，而不是再挂一跳。
6. **无人做上游请求体压缩**（CPA 与 keepalive-proxy 都没有），先不做。

|---|---|---|---|
| 下游响应压缩 | **无** | **无**（全仓库无 `gzip.NewWriter` 出现在响应路径，`Content-Encoding` 仅出现在 header 剥离表） | **无**（APISIX `config.yaml` 与 `apisix.yaml` 中无 gzip/brotli 配置，走默认） |

| SSE 保活（静默期补帧） | **无** | 无（有 stream 相关处理，但无静默期注入） | **有**，且是核心功能：`HEADER_WAIT`(2s) 后发协议原生首帧，此后每 `IDLE_INTERVAL`(15s) 静默补帧（`keepalive/main.go:586,622,800,821`） |

### 2.1 keepalive-proxy 的保活帧表（可直接照抄）

来自 `keepalive/main.go:821`：

| 协议路径 | 保活帧 | 终止事件 |
|---|---|---|
| `/v1/responses`、`/responses` | `data: {"type":"response.in_progress"}\n\n` | `response.completed` / `response.failed` / `response.incomplete` / `error` |
| `/v1/chat/completions` | `: keepalive\n\n`（SSE 注释帧，数据消费者不可见） | `[DONE]` 或顶层 `error` |
| `/v1/messages` | `event: ping\ndata: {"type":"ping"}\n\n` | `message_stop` 或 `error` |

配套的写帧语义（`keepalive/main.go:808`）：`w.Write` 后立即 `Flush`；出错即判定下游断开。慢启动时先 `Content-Type: text/event-stream` + `Cache-Control: no-cache` + `X-Accel-Buffering: no` + `200`，然后立刻发保活帧。

### 2.3 本仓库真实流量基线

来自 `logs/requests.restored.db`（`store-body` 关闭，故 body 长度为 0；token 统计有效）：

- 8,472 次请求，输入 token 合计 **约 10.7 亿**，缓存命中 token **约 9.8 亿**（约 92%，亲和策略有效）。
- 单次请求平均输入约 **12.6 万 token**——意味着每个请求体是数百 KB 到数 MB 量级的 JSON，反复在「客户端→网关→上游」两段链路上以未压缩形式传输。
- 主要来源：`pi`(6396)、`kimi-code-cli`(876)、`opencode`(864)、`omp`；路径分布 `/v1/responses`(5504)、`/v1/messages`(2266)、`/v1/chat/completions`(702)。
- 平均耗时可观（`/v1/chat/completions` 27s、`/v1/messages` 23.8s、`/v1/responses` 14.7s）——静默期保活的收益在这一量级下是实打实的。

| 编号 | 缺口 | 位置 | 影响 |
|---|---|---|---|
| G0 | 下游无任何响应压缩（JSON 与 SSE 都没有） | `internal/server/server.go` 全文 | 出口带宽与客户端首字节时间 |

## 4. 分阶段计划

排序原则：先做收益确定、改动集中、可独立验证的项；WS 放最后。每个阶段都必须默认保持现有行为不变（客户端不声明压缩时行为与今天完全一致）。

### 实施状态

| 阶段 | 状态 | 落地位置 |
|---|---|---|
| P0 下游响应压缩 | ✅ 已实现并端到端验证 | `internal/server/encoding.go` + `server.go` 中间件链 |
| P1 接受压缩请求体 | ✅ 已实现（gzip/deflate/zstd；br 返回 `415`） | `internal/server/encoding.go` `decodeBody` |
| P2 上游编码策略 | ✅ 改为「保留 identity + 配置守卫」（原因见 §9.2） | `internal/executor/executor.go` + `internal/config/config.go` |
| P3 SSE 静默期保活 | ✅ 已实现，含首帧等待期 | `internal/server/keepalive.go` + `forward` |
| P4 WebSocket | ⏸ 调研完成后建议不做（结论与依据见 §10） | — |

实测证据：

- `curl --compressed /v1/models` → `Content-Encoding: gzip` + `Vary: Accept-Encoding`；不带 `--compressed` 时逐字节等同旧行为。
- 静默 6s 的上游 + `stream: true`：客户端约 2s 收到 `data: {"type":"response.in_progress"}`，随后按 1s 间隔收到三个真实事件，终止事件后不再补帧；全程 gzip 压缩且事件仍逐个到达。
- 快 `429`（2s 内）→ 客户端仍收到真实 `HTTP 429`；静默 4s 后 `429` → 客户端收到 `HTTP 200` + `response.in_progress` + 协议内 `event: error`（message 为上游原文 `rate limited`）。
- zstd 请求体：471,336 字节 JSON 压成 1,084 字节送出 → 网关解出后上游收到 471,336 字节明文、`input` 400 项、无 `Content-Encoding`；同一请请求换 `br` 仍为 `415`。

### P0 — 下游响应压缩（收益最大，改动最集中）

**做法**

- 新增一个 `http.ResponseWriter` 包装层，放在中间件链 `s.auth.Middleware(s.limitBody(withRecover(...)))` 的内层，让 `/v1/*` 与 dashboard 的全部 JSON 都自动受益。
- 协商：仅当客户端 `Accept-Encoding` 声明了可用编码时启用；`identity` 或缺省则不压缩。压缩后不设 `Content-Length`，设 `Content-Encoding` 与 `Vary: Accept-Encoding`。
- 编码范围：**gzip（stdlib `compress/gzip`）优先落地**；zstd 需引入 `klauspost/compress/zstd`（flush 成本低，适合流式），按需再开。**brotli 流式不做**（flush 粒度差、CPU 高）。
- SSE：必须逐块 `gz.Flush()` 后再 `underlying.Flush()`，流结束时 `Close()` 以吐出末尾块。
- 只压缩 `application/json`、`text/event-stream`、`text/*`；图片/二进制（`/v1/images/*`）跳过。
- 非流式 JSON 加阈值（约 1KiB）避免小响应反而变大。

**必须注意的正确性陷阱**

- 包装层的 writer **必须实现 `http.Flusher` 并转发到底层**，否则 `forward` 里的 `w.(http.Flusher)` 断言失败，所有流式请求直接变成 `500 streaming not supported`（`server.go:711`）。
- `Accept-Encoding` 缺省时**不得**压缩，否则现有基于 `httptest` 的测试与本机 `curl` 默认行为都会变（这是保持测试绿色与向后兼容的关键）。
- 压缩层与 `usage.mergePayload` / `chunk.LogError` 的载荷解析互不影响（解析发生在写入之前），但**压缩 writer 必须原样透传 `Write` 的返回值语义**，否则 `forward` 里的 `writeErr` 断连判定会失真。

**验收标准**

- `curl -N --compressed -H 'Authorization: ...' -d '{...stream:true...}' /v1/responses`：能看到 `Content-Encoding: gzip`，且事件仍是**逐个到达**（不是全部攒完一次性出现），`[DONE]` / `response.completed` 正常。
- 非流式：`curl --compressed /v1/models` 返回 gzip 且 JSON 完整；不带 `--compressed` 时响应与今天逐字节一致。
- 记录同一 session 压缩前后的下行字节数（用 `--write-out '%{size_download}'` 或抓包统计），写入本文档的基线对比。

### P1 — 接受客户端压缩请求体

**做法**

- 在 `limitBody` 之后插入解压层：读取 `Content-Encoding`（`gzip` / `zstd` / `br`），把 `r.Body` 换成对应解码 reader，并在送往下游解析前删除 `Content-Encoding` 与 `Content-Length`（下游代码按明文 JSON 解析、gjson 取亲和键、可选落库）。
- **双重上限**（这是信任边界，不能省）：`MaxBytesReader` 限压缩后字节，解压后再套一层 `io.LimitReader`，超限返回 `413`（CPA 的做法可参照：`internal/api/max_request_body_bytes_test.go` 有 zstd 超限返回 413 的用例）。
- 顺序必须是「先限流、再解压」，否则解压炸弹绕过限制。
- 跳过 multipart（`/v1/images/edits`）与空 body。
- 依赖：gzip 用 stdlib；zstd/br 需要 `klauspost/compress/zstd` 与 `andybalholm/brotli`。若只做 gzip+zstd（客户端实际会用的），可先不引 brotli。

**验收标准**

- `gzip -c body.json | curl -H 'Content-Encoding: gzip' --data-binary @- ...` 与未压缩请求行为一致（含亲和命中、请求日志正常）。
- zstd 压缩的超限请求返回 `413`，进程不 OOM。

### P2 — 上游 `Accept-Encoding` 策略化

**做法**

**实际落地**：保留 `identity`（它是刻意的，不是遗漏），改为两件更小、更正确的事：

1. 在 `internal/executor/executor.go` 为 `identity` 写下理由：自动 gzip 解码只在收齐一个 deflate 块后才吐数据，上游若不逐事件 flush 就会把 SSE 事件攒成批，反而破坏增量性。
2. 在 `internal/config/config.go` 校验中拒绝 provider `headers` 里除 `identity` 以外的 `Accept-Encoding`——手动设置该头会关闭 transport 的透明解压，静默地把压缩正文交给解析器。

不做 `accept-encoding` 配置字段与 br/zstd 解码器：非流式请求已由 transport 自动 gzip + 透明解压，进一步手写解码只是给 slim 二进制增依赖，收益未经实测。

### P3 — SSE 静默期保活（把 keepalive-proxy 的能力内建）

**做法**

- 在 `forward` 的 `*executor.StreamResult` 分支加一个 ticker：
  - 首字节等待阈值（对齐 `HEADER_WAIT` = 2s）：超过则先提交 `200` + `Content-Type: text/event-stream` + `Cache-Control: no-cache` + `X-Accel-Buffering: no`，并发第一帧保活。
  - 此后每次下游静默超过 `IDLE_INTERVAL`（15s）补一帧；**任何真实上游数据到达都重置计时**。
- 帧表照抄 §2.1；用 lite-cpa 已有的 `usage.mergePayload` 解析顺带检测终止事件，终止后停止补帧（避免终止事件之后再出现合成帧）。
- 配置项建议：`sse-keepalive: true|false`（默认关闭以保持现行为）、`sse-keepalive-interval`、`sse-keepalive-first-frame-wait`。
- 与 P0 的关系：**两者不冲突**，因为保活帧由 lite-cpa 自己生成（上游压缩由 Go/自有解码器负责），帧写入后再走下游压缩层逐块 Flush 即可。这与 keepalive-proxy 被迫用 `identity` 的处境不同——它需要做字节级 `validSSE()` 校验，而 lite-cpa 本来就解析载荷。

**验收标准**

- 用一个人为延迟首字节、且中途静默 40s 的假上游：`curl -N` 在 2s 内看到第一帧，之后每约 15s 一帧，真实事件到达后保活停止。
- 长 thinking 的真实请求不再出现下游超时断连（对比改造前后 `outcome=client_canceled` 的比例）。
- 终止事件之后不再出现任何合成帧。

### P4 — WebSocket（拆成两步，先便宜后昂贵）

**P4a 原始隧道（便宜，建议先做）**

- 对 `GET /v1/responses` 带 `Upgrade: websocket` 的请求，用 `http.Hijacker` 把下游连接到「支持 WS 的 provider」建立的上游 WS 之间做双向 `io.Copy`；101 与握手头原样透传。
- permessage-deflate 因为是端到端透明隧道，天然协商成功，无需在网关侧实现压缩。
- 对不支持 WS 的 provider：返回明确的 HTTP 状态（而不是挂着一个半死连接），让客户端回落 SSE——Codex 有 `websocket closed by server` 的路径，实测确认回落行为后固化。
- provider 侧需要一个新的能力开关（例如 `websocket: true`），避免对中转站乱升级。

**P4b 终止式桥接（昂贵，按需）**

- 下游 WS 终止 + 上游仍是 SSE；需要维护 per-connection 状态：
  - 支持 `previous_response_id` 的上游：直传。
  - 不支持的上游：必须自己重放 transcript（CPA 的 `normalizeResponsesWebsocketRequestWithIncrementalState` 就是这件事，还包含 Codex local compaction replay 绕过）。
- Ping/Pong 保活独立于 turn 进度（读循环与写 Ping 必须并发，否则 Pong 无法被确认——keepalive-proxy 的 README 专门记录了这个坑）。
- **这一项才是「增量 WS 省流量」的真正来源**：客户端只发增量而非全量上下文。按 §2.3 的基线（平均 12.6 万输入 token/次），对 Codex 类客户端收益巨大，但只覆盖 Codex 系客户端，且实现量远大于 P0–P3。

**验收标准（P4a）**

- Codex CLI 配置 `prefer_websockets = true` 时能通过 lite-cpa 建立 WS 并完成多轮；抓包确认 permessage-deflate 协商成功。
- 上游不支持 WS 时，客户端能在可接受时间内回落 SSE 并成功完成请求。

## 5. 明确不做（YAGNI）

| 项 | 理由 |
|---|---|
| 非流式 `103 Early Hints` 心跳 | AI-gateway 自己的归档文档记录了 cloudflared 会吃掉 103、quick tunnel 约 126s 仍 524；收益不确定且与部署链路强耦合 |
| Gemini `wsrelay` 反向中继 | 那是 CPA 为「客户端反向连接转发 Gemini 请求」设计的，与 lite-cpa 的转发模型不同 |
| 终止式 WS 的网关侧 permessage-deflate 重协商 | 原始隧道（P4a）天然端到端支持，重协商是纯新增复杂度 |
| brotli 下游流式压缩 | flush 粒度差、CPU 成本高；gzip 已经覆盖绝大多数客户端 |
| 上游请求体压缩 | 三个参照实现都没做，且无证据表明上游接受 `Content-Encoding: gzip/zstd` 的请求体；如未来要做，按 provider 开关 |
| 压缩中间件的「按内容类型/大小阈值」精细策略引擎 | 先用固定白名单 + 1KiB 阈值，等出现真实反例再加规则 |

## 6. 风险清单

1. **Flusher 断言失效**（P0）：包装 writer 不实现 `http.Flusher` 会让所有流式请求 500。必须实现并转发，且要有测试覆盖。
2. **压缩 + 逐块 Flush 的兼容性**（P0）：gzip `Flush()` 会产生 sync flush 块，合规解码器可在流中解出；但若客户端用了「整体缓冲解码」的实现（少见），增量性会被破坏。验收标准里必须显式检查事件是逐个到达。
3. **默认行为不得改变**（P0/P1）：任何未声明 `Accept-Encoding` 的客户端必须拿到与今天逐字节一致的响应；现有测试套件是这条的守门人。
4. **自己设 `Accept-Encoding` 即失去 Go 透明解压**（P2）：这是最容易踩的单行陷阱，必须配套解码 reader，否则流式与错误体都会静默损坏。
5. **解压炸弹**（P1）：压缩上限与解压后上限必须分开设置，顺序不能反。
6. **部署链路上的重复压缩**（P0）：如果前置 nginx/Cloudflare 已经开启 gzip，网关再压会变成「压了又解、解了又压」。落地时二选一，并在部署文档里写明。
7. **链路代理会否破坏 SSE 增量**：`X-Accel-Buffering: no` 需要补上；nginx 需 `proxy_buffering off`（README 已有部署提示）。
8. **保活帧被客户端当成业务事件**（P3）：`chat/completions` 用 SSE 注释帧最安全；`/v1/responses` 注入 `response.in_progress` 与 `/v1/messages` 注入 `ping` 需对真实客户端实测，必要时改成仅对声明支持的路径启用。
9. **WS 回落行为依赖客户端实现**（P4a）：需要实测确认，而不是假设。

## 9. 实施中发现的两个关键事实

### 9.1 保活必须覆盖「等首个事件」，而不只是事件之间的空隙

原计划把保活放在 `forward` 的 `*executor.StreamResult` 分支里，默认了「上游 200 已到、只是正文静默」。实测推翻了这一点：`streamPassthrough`（同格式流式的主路径，`internal/executor/executor.go`）会先 `readSSEEvent` 读一个事件、检查 `semanticSSEError` 才返回，**所以 `execute` 返回前客户端连 200 响应头都拿不到**。

因此保活改为：对 `stream: true` 的请求，在调用 `execute` 之前就武装定时器；首帧等待期（默认 2s）一到就先提交 `200` + `text/event-stream` 并发出协议帧。代价是已提交的流不能再改变 HTTP 状态码，晚到的失败改为协议内错误事件（§9.3）。同时该尝试改到独立 goroutine 执行并与定时器赛跑，客户端断开时不再需要等上游开口才能释放 lease。

注：`sse-keepalive: false` 时完全不进入该分支——同步执行、无早提交、无 goroutine，与改造前逐行等价（既有 `TestForwardPanicReleasesLease`、`TestForwardCancellationAccounting` 原封不动通过，正是这条等价的证据）。

### 9.2 `identity` 是有意为之，不是遗漏

`doClaude` 流式路径的 `Accept-Encoding: identity` 原本无任何注释，看起来像可以「顺手清理」的一行。实际上：Go 的自动 gzip 解码要收齐一个完整 deflate 块才吐出数据，上游若不逐事件 flush，就会把 SSE 事件攒成批，反而破坏增量性——而这正是本次要解决的问题。

于是 P2 从「加配置字段 + 引入 br/zstd 解码器」收敛为「写清理由 + 拦住误配置」：校验器现在拒绍 provider `headers` 中除 `identity` 以外的 `Accept-Encoding`（手动设置它会静默关闭透明解压）。

### 9.3 「保活」与「HTTP 状态码」不可兼得

必读的语义边界：字节一旦上线，状态码就定死了。因此：

- 失败在首帧等待期内到达（中转站快速 `429` 的常见情形）→ 仍是真实 HTTP 状态码。
- 失败在提交之后到达 → 协议内错误事件（Responses `event: error` / Chat `error` 对象 + `[DONE]` / Messages `event: error`），不再暴露 HTTP 细节。
- 内部多 key failover 两种情况都照常进行。

需要严格的「错误必须是状态码」语义时，设 `sse-keepalive: false` 即可回到今日行为。

## 10. P4 WebSocket：调研后的结论

### 10.1 事实（均来自 primary source）

1. **客户端不是默认就会发 WS**。Codex CLI 在 `codex-rs/model-provider/src/provider.rs` 中，**自定义 provider 的 `supports_websockets` 默认 false**；`codex-rs/model-provider-info/src/lib.rs` 持有该字段，`codex-rs/core/src/client.rs` 的 `responses_websocket_enabled()` 以它为主开关。也就是说：网关要想收到 WS 请求，用户还得在 Codex 配置里手动打开这个开关。
2. **降级是干净的**。`responses_websocket.rs` 的 `connector.rs` 连的是 `provider.websocket_url_for_path("/responses")`，不加子协议；`client.rs` 里有 `WebsocketStreamOutcome::FallbackToHttp` 与会话级 fallback 状态 —— 握手失败会回落 SSE，不是硬错。所以今天「不支持 WS」不会弄坏客户端，只是回到全量重发。
3. **原始隧道对当前配置是死代码**。`config/config.yaml` 启用的上游是 `api.mayoru.com`、`host.docker.internal:3425`、`10.126.126.11:8317`，均为中转/自建 HTTP 聚合，不提供 Responses WS 端点。
4. **真正的桥是 CPA 量级的工程**。CPA 的 WS 实现约 4000 行生产代码（`openai_responses_websocket*.go`：transcript 合并、full-transcript/compaction replay 判定、steering、prewarm、tool-call 修复缓存、时间线日志）加约 8000 行测试。原因很实在：上游 SSE 不支持 `previous_response_id` 时，网关必须自己把增量输入合并回完整 transcript，而合并要处理 `function_call`/`function_call_output` 配对、compaction 替换、未完成 tool call 等边界。

### 10.2 两条路线与代价

| 路线 | 能工作当 | 代价 | 适合本仓库？ |
|---|---|---|---|
| P4a 原始隧道（hijack + 帧转发） | 客户端开 `supports_websockets` **且** 选中的上游本身说 Responses WS | 一个 WS 依赖（帧解析不手写）+ provider 能力位 + 逐帧 model 重写；~300 行 | ❌ 对当前全中转站配置无用 |
| P4b 下行终止 + 上游 SSE 桥 | 任意 SSE 上游，包括中转站 | transcript 合并状态机 + tool-call 修复 + 测试；CPA 量级 | ❌ 与 slim gateway 定位正面冲突 |

### 10.3 建议

**不做 P4，除非其中一条成立**：

- 真的接入了一个原生支持 Responses WS 的上游（官方 OpenAI / xAI / 自建 CPA），此时 P4a 值得做；
- 你愿意接受 P4b 的体量，并接受「网关自己维护 session transcript」带来的新失效模式。

在那之前，客户端的回落行为（SSE + 全量重发）配合已经落地的 P0/P3（下游压缩 + 静默期保活）已经是可用状态；而**上行大 body 的真正浪费已在 P1 解决**：客户端只要肯压缩请求体（Codex 用 zstd 压 compacted transcript），就是 5～8 倍的实利，且网关侧零协议风险。
