# 渠道亲和、重试与故障切换

lite-cpa 如何把会话钉在上游 API key 上、信任哪些 CLI 身份字段、何时重试、中转站应如何切换。

会话身份提取的源码真源：

```text
internal/affinity/cli_sessions.go
```

配置与部署见 [AGENTS.md](../AGENTS.md)。English: [Channel Affinity and Retry](Channel-Affinity-and-Retry.md)。

---

## 为什么需要亲和

多 key / 多供应商能提高可用性，但 **prompt cache 和会话状态通常绑在单一上游凭证上**。同一 CLI 会话若在不同 key（或不同中转）之间乱跳，缓存命中率会掉，行为也可能不一致。

渠道亲和是一层 **成功记忆**：

1. 从请求中提取 **会话身份**（先 header，再 body）
2. 上游 **成功** 后，记住服务该身份的 `UpstreamKey.ID`
3. 之后同一身份优先用这把 key

它 **不是** 普通负载均衡。没有 pin、或 pin 被清掉 / 过期时，仍走优先级与轮询。

---

## 钉住的是什么

lite-cpa 只做 API-key 上游（无 OAuth 账号）。映射关系：

```text
会话身份  →  UpstreamKey.ID   （如 laysath-0）
```

`UpstreamKey.ID` 形如 `{provider-name}-{index}`，不是单独的供应商展示名。

缓存键：

```text
cacheKey ≈ "{规则名}:{亲和值}"  →  UpstreamKey.ID
默认 TTL：600 秒（仅进程内存，无 Redis）
```

| 事件 | 行为 |
|---|---|
| Lookup 命中 | 首次尝试优先用该 key（仍在该模型 key 池内） |
| Lookup 未命中 | 普通优先级 / 轮询 |
| 上游 **成功** | `Record` pin（`switch-on-success` 默认 true → 钉真正成功的那把） |
| sticky key **失败** | `Clear` 该 cache key 的 pin |

没有身份字段 → 亲和完全不生效。

## 何时会粘住

两个条件都要满足。

### 1. 模型族要匹配

默认模型族（亲和开启且未写自定义 `rules`）：

`claude`、`gpt`、`gemini`、`grok`、`glm`、`kimi`、`qwen`、`minimax`。

匹配方式：**子串、不区分大小写**（`proxy-claude-x` 能命中 `claude`）。

YAML：

```yaml
channel-affinity: true                 # 默认全部模型族
channel-affinity: [claude, gpt, grok]  # 子集
channel-affinity: false                # 关闭
channel-affinity:
  models: [claude, grok]
  default-ttl-seconds: 600
```

高级：写 `rules:` 可完全覆盖生成的族规则。亲和开启且 `rules` 为空时，由 `models` / 默认族展开。

### 2. 必须有会话身份

运行时提取顺序：

```text
1. 粘性 Session 请求头  （StickySessionHeaders — 第一个非空胜出）
2. 按路径的协议 body
3. 规则剩余 KeySources（仅自定义规则；catalog 头已试过）
```

**没有** 消息内容哈希兜底。无身份 → 纯轮询 / 优先级。

#### Header 优先级（运行时）

第一个非空 header 生效。产品级稳定 id 在前，弱 / 可能每请求的在后：

| 优先级 | Header | 典型 CLI |
|---|---|---|
| 1 | `X-Claude-Code-Session-Id` | Claude Code |
| 2 | `x-opencode-session` | OpenCode |
| 3 | `x-session-affinity` | **MiMo Code**、OpenCode / Pi 亲和 |
| 4 | `session-id` / `Session-Id` / `session_id` | Codex、Pi |
| 5 | `thread-id` / `Thread-Id` / `thread_id`、`Conversation_id` | Codex thread / WS |
| 6 | `X-Session-Id` | 通用 / OpenCode / Pi openrouter 格式 |
| 7 | `x-parent-session-id` | 子 agent 父会话（较弱） |
| 8 | `X-Amp-Thread-Id` | Amp CLI |
| 9 | `X-Client-Request-Id` | Pi（Codex 上可能是每请求 UUID，故放最后） |

`net/http` 对 header 名大小写不敏感；同时列出连字符与下划线写法，是因为反代行为不一致。

弱信号头（`X-Client-Request-Id`）会被延后：只有当强 header、协议 body 字段、自定义 key source 都取不到身份时才使用，且由弱值建立的粘性条目 TTL 上限为 60s——弱值可能是每请求变化的，完整 TTL 会用一次性键灌满缓存。

#### 协议 body（没有 session 头时）

| 请求路径 | 优先 body 字段（顺序） |
|---|---|
| 含 `/messages` | `metadata.user_id` → `prompt_cache_key` |
| `/responses`、`/chat/completions`、`/completions` | `prompt_cache_key` → `metadata.user_id` |
| 其它 | `prompt_cache_key` → `metadata.user_id` |

**Claude / OpenCode `metadata.user_id` 归一化**（用到该字段时）：

| 格式 | 示例 | 写入亲和缓存的值 |
|---|---|---|
| 旧字符串 | `user_{hash}_account__session_{uuid}` | `{uuid}` |
| JSON 字符串 | `{"device_id":"...","session_id":"uuid"}` | `{uuid}` |
| 其它非空 | 任意字符串 | 原样 |

## 编码类 CLI 总表

目录在 `PriorityCLISessionSources`（`cli_sessions.go`）。运行时 **不会** 先识别 CLI 再取字段——统一走共享 header 列表 + body 路径。下表说明 **各 CLI 实际发出什么**，以及反代应保留什么。

| CLI | 置信度 | 主 sticky 信号 | 次要 | 备注 |
|---|---|---|---|---|
| **claude-code** | high | body `metadata.user_id`（归一化）；头 `X-Claude-Code-Session-Id` | — | Claude Code 会话格式 |
| **codex** | high | 头 `session-id` / `session_id`、`thread-id`；body `prompt_cache_key` | `Conversation_id` | **不要**单独把 `X-Client-Request-Id` 当会话（常为每请求） |
| **pi** | high | `session_id`、`x-session-affinity`、`X-Session-Id` | `X-Client-Request-Id`、body `prompt_cache_key` | `sessionAffinityFormat`：openai / openrouter |
| **oh-my-pi** | high | 同 Pi | 同 Pi | 与 Pi 共用 openai-shared 栈 |
| **opencode** | high | `x-opencode-session`、`x-session-affinity`、`X-Session-Id` | body Claude 式 `metadata.user_id` | 在 **入口** 读头（发往真实 provider 前可能被剥掉） |
| **kimi-code** | high | body **`prompt_cache_key`**（= session id） | `metadata.user_id` | 仓库内无稳定 sticky HTTP 头。**不要**用 `X-Msh-Device-Id` |
| **mimo-code** | high | 头 **`x-session-affinity`** = sessionID | `x-parent-session-id`、OpenCode 遗产头 | OpenCode fork；`User-Agent: mimocode/...` 只用于识别客户端，不是 pin key |
| **zcode** | medium | Claude 式 `metadata.user_id` | 常见 session 头 | Claude 兼容表面 |

### 反代：不要剥掉的头

至少透传：

```text
X-Claude-Code-Session-Id
x-opencode-session
x-session-affinity
x-parent-session-id
session-id / session_id
thread-id / thread_id
Conversation_id
X-Session-Id
X-Client-Request-Id
X-Amp-Thread-Id
```

Nginx 默认丢弃带下划线的 header，除非 `underscores_in_headers on`。能控客户端时优先连字符形式；仍需接受 Codex / Pi 的下划线写法。

流式还需关闭响应缓冲（如 `proxy_buffering off`）。

## 重试次数

由顶层 `request-retry` 控制：

```text
maxAttempts = min(1 + request-retry, 该模型可用 key 数)
```

例如 `request-retry: 2` 且有 5 把 key → 单次请求最多 **3** 次尝试。

可触发换 key 的上游结果：

- HTTP **401 / 403 / 429 / ≥500**
- 网络 / 传输错误

其它 4xx 直接回客户端，不轮转。

**同请求内没有按时间 backoff**，失败后立刻换下一把。

---

## 故障切换模式（按 provider 的 `name`）

可重试失败后，行为取决于 **失败那把 key 所属** 的供应商：

| `failover-mode` | 行为 | 适用 |
|---|---|---|
| `key`（默认） | 标记本 key 已试，换下一把未用 key（可能仍在同站） | 官方多 key、key 级限流 |
| `provider` | 本请求内跳过该 `name` 下 **全部 key** | 中转站（一站挂则 key 全废） |

```yaml
- name: openai-official
  failover-mode: key
  base-url: https://api.openai.com/v1
  ...

- name: laysath
  failover-mode: provider
  base-url: https://ai.laysath.cn/v1
  ...
```

多个供应商配置 **相同客户端 `alias`** 时，key 会 **合并** 成一个池；选路先比 provider `priority`，再比该 provider 内 entry `priority`，最后轮询。

---

## 亲和 × 重试 × 切换（单次请求）

```text
1. 查亲和 → 可选 preferred key
2. 循环（≤ maxAttempts）：
     优先 sticky，否则 Selector.Pick
       - 尽量同供应商
       - 跳过已标记死亡的供应商（provider 模式）
     调上游
     失败：
       若是 sticky key → Clear pin
       若 skip-retry 且用过 sticky → 停止
       若 failover-mode=provider → 跳过整个 name
       continue
     成功：
       Record pin → 返回
3. 返回最后错误
```

### 生产相关默认值

| 配置 | 默认 | 用意 |
|---|---|---|
| 亲和开启 | 默认开 | 利于会话缓存 |
| 亲和 TTL | **600s** | 避免长时间粘死中转 |
| 族规则 `skip-retry-on-failure` | **false** | 允许故障切换；成功再 pin |
| `switch-on-success` | true | 钉真正成功的 key |
| `failover-mode` | 未写则 `key` | 中转请显式 `provider` |

## 常见坑（「为什么还打旧渠道」）

1. **TTL 未到期** — pin 最多保留 600s（或你设的 `default-ttl-seconds`）。
2. **自定义规则 `skip-retry-on-failure: true`** — sticky 失败后本请求不换。
3. **中转仍用 `failover-mode: key`** — 会在同站换 key。应改为 `provider`。
4. **新加了更高优先级供应商** — 已有 pin 仍优先旧 key，直到清除/过期。
5. **请求没有身份字段** — 亲和根本不生效。常见原因：反代剥掉了 session 头，或客户端未发 `prompt_cache_key` / `metadata.user_id`。
6. **进程重启** — 内存缓存清空（无 Redis）。
7. **Kimi** — 粘性依赖 body `prompt_cache_key`；设备类 header 不是会话键。
8. **MiMo / OpenCode** — 入口需保留 `x-session-affinity`（或 `x-opencode-session`）。

当前 **没有** 管理端「清空亲和缓存」接口。实用手段是短 TTL、重启；失败路径已会 Clear 对应身份。

## 推荐配置

### 仅官方

```yaml
request-retry: 2
openai-responses:
  - name: openai-official
    failover-mode: key
    base-url: https://api.openai.com/v1
    api-key: sk-...
    models: [{ name: gpt-5, alias: gpt-5 }]
```

### 官方 + 中转（同 alias 合并池）

```yaml
request-retry: 3
openai-responses:
  - name: openai-official
    priority: 0
    failover-mode: key
    base-url: https://api.openai.com/v1
    api-key: sk-official
    models: [{ name: gpt-5, alias: gpt-5 }]

  - name: laysath
    priority: 1
    failover-mode: provider
    base-url: https://ai.laysath.cn/v1
    api-key-entries:
      - { api-key: sk-a }
      - { api-key: sk-b }
    models:
      - { name: gpt-5, alias: gpt-5 }
      - { name: grok-4.5, alias: grok-4.5 }
```

### 亲和开关

```yaml
channel-affinity: true                    # 或 [claude, gpt, grok]
# channel-affinity: false
# channel-affinity:
#   models: [claude, grok]
#   default-ttl-seconds: 600
```

## 调试

`debug: true` 时 stderr 会打 affinity hit / clear / record 与轮转日志。

`GET /api/affinity/stats`（需网关密钥，与 `/api/logs` 一致）只返回计数器：`matched_lookups`、`cache_hits`、`hit_rate`、`records`、`clears`、`preferred_unavailable`、`entries`，不暴露任何亲和值与缓存键。

可选 request-log 会记供应商名与状态码，尚不包含亲和指纹字段。

验证某 CLI 身份：带上预期 header/body 发一请求，开 debug 看 `affinity recorded`；第二次应出现 `affinity hit` 且 key id 相同。
